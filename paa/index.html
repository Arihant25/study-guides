    Two oxen, 1024 chickens, or a million chicks?

    Seymour Cray asked which you'd rather plough a field with. GPUs answered: a million tiny, simple workers, marching in lockstep groups of 32. This guide is the whole course, L1 to Model Compression, told through things you can poke.

    2 oxenFew powerful vector processors. Cray-1, 1970s.
    1024 chickensClusters of ordinary microprocessors. 1990s–2000s.
    a million chicksGPUs. Top500 from Nov 2010; 90%+ of compute today.

    Each level has short concept cards, a lab to play with, and a checkpoint quiz. Right answers on the first try earn 10 XP. Red dashed boxes flag places where the slides are loose or have a bug, which makes good exam bait.

    Level 1

    Why we needed accelerators

    The free lunch ended, gamers paid for the hardware, and AI turned out to be mostly matrix multiplication. Moving data costs far more energy than doing the maths.

    From L1 · Introduction
    1965 · Moore

    Transistors double every ~2 years

    An economic observation the industry worked hard to make true.

    1974 · Dennard

    Shrink 30%, power density stays flat

    Area −51%, delay −30%, frequency +40%, power −51%. Twice the transistors at the same power: a literal free lunch.

    ~2005 · Power wall

    Leakage killed it

    Voltage couldn't keep dropping (electrons tunnel), so chips ran too hot. Answer: multicore, which is hard to program.

    How GPUs crept in

    • Graphics = same simple op on every pixel. Parallel by nature.
    • 2001: programmable shaders. People "tricked" them into MatMul, FFT, sorting.
    • 2002: "GPGPU" coined (Mark Harris). 2006: CUDA + 8800 GTX, ~500 GFLOPs for $300.
    • 2012: AlexNet on 2 GTX 580s beats ImageNet by ~10%. Deep learning's big bang.

    Why it costs so much

    • 1 GW datacenter ≈ 1 million GPUs at ~1 kW each.
    • Hardware ≈ $60–65B. Power ≈ $700M/year at $0.08/unit.
    • Training ≫ inference per run, but inference happens billions of times.
    • So: optimise system software, algorithms, number formats and architecture together.

    Ranges per bit from the L1 energy table, on a log axis. A memory access can cost 100× an arithmetic op, and caches over-fetch whole lines.

    Level 2

    Ways to be parallel

    Classify parallel machines by instruction and data streams, by where the parallelism comes from, and by how memory is shared. Then measure algorithms by work, not just time.

    From L2 · Parallel Computing
    Lab 2A · Flynn's taxonomy (1966)

    Click a quadrant

    Single data
    Multiple data
    Single
    instruction
    Multiple

    Data parallel

    Same F, different chunks

    Chunk 1…N each run F, then combine. This is the GPU's home turf.

    Task parallel

    Different code per worker

    Parse input, render image, write log, all at once.

    Pipeline parallel

    Stages in flight

    Item 1 at stage 3 while item 3 is at stage 1. Like the CPU's fetch–decode–execute.

    Shared memory (SMP)

    One address space on a bus. Fast sharing; the bus limits scaling.

    Distributed (MPP)

    Private memory per node. Every remote access is an explicit message.

    NUMA

    One address space, but local memory is fast and remote memory goes over the interconnect.

    PRAM model

    n processors, one shared memory. Variants by how conflicts are allowed:

    • CRCW concurrent read, concurrent write
    • CREW concurrent read, exclusive write
    • EREW exclusive both

    A GPU looks roughly PRAM-like: uniform access to one big global memory.

    CPU vs GPU

    • CPU: few complex cores, caches, branch prediction, out-of-order. Great at irregular work.
    • GPU: thousands of simple cores. Memory is ~500× slower than compute.
    • So a GPU needs high arithmetic intensity and thousands of threads to hide latency.
    Lab 2B · Work efficiency

    Fast isn't the same as efficient

    W(n) = Tp(n) × p · efficient ⇔ Wp(n) = Ws(n)

    Tree reduction and Blelloch scan do the same O(n) work as the sequential loop. Hillis–Steele scan finishes in log n steps but does O(n log n) work. Merge sort and matmul have efficient parallel versions; DFS and GCD don't.

    Level 3

    Inside the GPU and CUDA

    The host launches a grid of blocks. Each block lands on one SM and is chopped into warps of 32 threads that run one instruction in lockstep. Almost every performance rule follows from this.

    From L2–L3 · GPUs and Data Parallel Computing, Tutorial 1
    Logical (what you write)
    • Grid · gridDim, blockIdx
    • Block · 1–1024 threads, 1D/2D/3D, can share memory and __syncthreads()
    • Warp · 32 threads, the scheduling unit (a hardware detail, not part of the model)
    • Thread · threadIdx
    Physical (what runs it)
    • Device · RTX 5090: 170 SMs, 21,760 CUDA cores, 32 GB, 1.8 TB/s
    • SM · 128 cores in 4 sub-cores, 4 Tensor Cores, 256 KB registers, 128 KB L1/shared
    • Limits / SM · 64K regs, ≤255 per thread, 2048 threads, 32 blocks
    • L2 96–128 MB · Global HBM/GDDR
    // Tutorial 1: launch, index, copy
kernel<<<blocksPerGrid, threadsPerBlock>>>(args);
int idx = blockIdx.x * blockDim.x + threadIdx.x;      // map thread → data
cudaMalloc(&d_x, bytes);                               // GPU memory is separate
cudaMemcpy(d_x, h_x, bytes, cudaMemcpyHostToDevice);   // explicit copies
// grid-stride loop: one launch handles any N
for (int i = idx; i < N; i += blockDim.x * gridDim.x) y[i] = a*x[i] + b*y[i];

    If a register read took 1 second…

    Cycle counts from L3. This gap is why the SM keeps many warps resident: when one stalls on memory, another runs the next cycle with zero switching cost, because registers and shared memory are already partitioned.

    Lab 3C · Occupancy

    How many threads can live on one SM?

    Slide catch: the L3 examples divide by 256 KB of shared memory, but the same slide says the SM has 228 KB. Use whatever the question gives you. Also, low occupancy isn't automatically bad (see Level 6, Volkov).
    Lab 3D · Shared-memory banks

    32 banks, one address per bank per cycle

    float foo = shared[base + s * threadIdx.x]; bank = word_index % 32

    Conflict degree = gcd(s, 32), so odd strides are conflict-free. Everyone reading the same word is a broadcast, also free. Structs: a 3-float struct is fine, a 2-word struct gives 2-way conflicts, hence "struct of arrays beats array of structs".

    Lab 3E · Global-memory coalescing

    One warp loads 32 floats. How many 32-byte sectors move?

    Lab 3F · Warp divergence

    A 128-thread block = 4 warps. Pick a branch.

    Amber lanes take then, teal take else. A warp holding both colours runs both paths one after another. Make the branch granularity a multiple of 32 and divergence disappears.

    Level 4

    Reduce, scan, transpose

    Blelloch's building blocks. Get these fast once and you can build almost anything. Each one teaches a hardware lesson: divergence, bank conflicts, work efficiency, coalescing.

    From L3–L4 · Data Parallel Algorithms, Tutorial 2
    Lab 4A · Reduction race

    Interleaved vs sequential addressing

    Scaled down: 16 elements and pretend warps of 4 threads (real warps are 32). A red underline marks a warp where some threads add and some sit idle.

    Slide catch (L4, "A better implementation"): for (int stride = blockDim.x; stride > 1; stride >> 1) never changes stride (needs >>=), starts one level too high and stops before stride 1. The L3 version is the correct one: for (stride = blockDim.x/2; stride > 0; stride /= 2).

    16M-element AND reduce

    • 1024 blocks × 256 threads = 262,144 threads
    • 2²⁴ / 262,144 = 64 elements per thread via grid-stride loop, into a register
    • Shared-memory tree 256 → 128 → 64 with __syncthreads()
    • Last warp finishes without barriers
    • One atomicAnd per block combines the 1024 results

    Warp finish: then vs now

    Pre-Volta: volatile shared memory and no sync, because the 32 threads shared one program counter. From Volta on, each thread has its own PC, so that trick isn't guaranteed. Use registers and shuffles:

    for (int off = 16; off > 0; off >>= 1)
  v += __shfl_down_sync(0xffffffff, v, off);
    Lab 4B · __shfl_down_sync

    Each lane grabs the value from lane + offset

    Lanes past the end keep their own value. Tutorial 2 check: lane 0 should end with 0+1+…+31 = 496.
    Lab 4C · Scan

    Prefix sum, two ways

    Hillis–Steele: at distance d, every i ≥ d adds x[i−d], double-buffered to avoid a race. Blelloch: up-sweep builds a reduction tree (n−1 adds), set the root to 0, down-sweep passes sums down (left child gets parent, right gets parent + old left).

    Transpose, three versions

    • Naive B[j*N+i] = A[i*N+j]: reads coalesced, writes 32 floats apart.
    • Shared tile: read a 32×32 tile row-wise, write it out row-wise from tile[tx][ty]. Both global sides coalesced, but the column read is a 32-way bank conflict.
    • Padded tile[32][33]: each row starts one bank later. Conflict gone for 32 floats of waste. Try stride 32 vs 33 in Lab 3D.

    Summed-area table

    Each cell = sum of everything above-left. Any rectangle sum then takes 4 lookups.

    SAT(A) = Tᵀ(rowScan(Tᵀ(rowScan(A))))

    Column scans are hard in row-major, so transpose, scan rows, transpose back.

    Lab 4D · SAT

    Click two corners of a rectangle

    Pick a top-left cell, then a bottom-right cell.
    Slide catch: the L4 formula mixes up indices. With inclusive SAT S and rectangle rows r1..r2, cols c1..c2: sum = S[r2][c2] − S[r1−1][c2] − S[r2][c1−1] + S[r1−1][c1−1] (terms with −1 indices are 0).
    Level 5

    What the GPU is actually running

    Neural networks are stacks of matrix multiplies with nonlinearities in between. Training loops forward, loss, backward, update. Convolutions become a GEMM through im2col.

    From L5 · ML Workloads (Girish Varma)
    Programming

    Shortest path in G → write Dijkstra.

    Machine learning

    Which digit is this? → collect (image, digit) pairs, fit a model y = fθ(x), then run inference on new images.

    Layers
    • Perceptron: y = σ(Σ wᵢxᵢ + b)
    • Fully connected: Y = σ(WX + b)
    • MLP: Y = σ(V σ(WX + b) + c)
    • Batch B inputs: (N×M)·(M×B) is a matrix–matrix product
    Lab 5A · Softmax

    Logits in, probabilities out

    softmax(z)ᵢ = exp(zᵢ − max z) / Σⱼ exp(zⱼ − max z)

    Subtracting the max changes nothing mathematically but stops exp from overflowing. On a GPU, naive softmax reads the row three times (max, sum, write). Online softmax fuses max and sum into one pass; see the case study.

    Lab 5B · The training loop

    One minibatch at a time

    sample minibatch→forward pass→mean loss (MSE / cross-entropy)→backward pass (last layer → first)→θ ← θ − η∇L↺

    Overfitting: training accuracy keeps climbing while test accuracy (data never used for gradients) stalls and drops.

    Why CNNs

    • Idea 1: connect each output only to a small window
    • Idea 2: share the same weights across positions
    • Gives translation invariance; pooling has no parameters
    • LeNet → AlexNet (8 layers, 62M) → VGG-19 (144M) → ResNet-50 (25.6M)

    Efficiency metrics

    • #Parameters (memory, model size)
    • MACs (compute)
    • Latency: time for one input
    • Throughput: inputs per second (batching helps this, not latency)

    Level 6

    Matrix multiplication, the main event

    FC layers, im2col convs and attention all reduce to GEMM. The whole game is reuse: shared memory turns O(N³) DRAM reads into O(N²), and registers multiply each shared-memory read into many FMAs.

    From L6 · Matrix Multiplication (after Simon Boehm's worklog)
    Step 1 · Naive

    One thread per C[i][j]

    Reads a row of A and a column of B: 2K loads for 2K FLOPs. AI = 0.25 FLOP/B, whatever the size. Fix the thread layout first so accesses coalesce.

    Step 2 · Shared tiles

    Block owns a C tile

    Stage BM×BK of A and BK×BN of B in shared memory, sync, accumulate, slide along K.

    Step 3 · Register blocking

    Thread owns 8×8

    Per k: read 8 A + 8 B values into registers, do the 8×8 outer product. 16 shared reads → 64 FMAs.

    for k in 0..BK:                       // inner loop of the 2048³ kernel
  for i in 0..TM: regM[i] = As[k][row+i]   // As stored transposed → no bank conflicts
  for j in 0..TN: regN[j] = Bs[k][col+j]
  for i, j:       acc[i][j] += regM[i] * regN[j]   // 64 FMAs in registers
    Lab 6A · Tile size vs arithmetic intensity

    Bigger tiles, more reuse

    AI = 2·BM·BN·K / (K·(BM+BN)·bytes) → square T: FP32 = T/4, FP16 = T/2

    Lower occupancy, on purpose

    ~100+ registers × 256 threads → only 1–2 blocks per SM, 25–50% occupancy. That's fine: each thread has 64 independent FMAs in flight, so instruction-level parallelism hides latency instead of more warps (Volkov, GTC 2010). Reaches ~90–95% of cuBLAS.

    Tensor Cores via WMMA

    Same block tiling, but the innermost op becomes a warp-wide 16×16×16 mma_sync: 4,096 MACs in one instruction. 16 calls replace 65,536 scalar FMAs. FP16 in, FP32 accumulate.

    The catch: the FP16 ridge on A100 is ~201 FLOP/B, so even T=256 (AI 128) isn't enough alone. Real kernels add L2 reuse across blocks (swizzling).

    Level 7

    Roofline and profiling

    Every kernel is limited by compute or by memory bandwidth. One log-log plot tells you which, and how far you are from the ceiling, before you waste days optimising the wrong thing.

    From L7 · Performance Analysis (Williams, Waterman & Patterson, CACM 2009)

    P(I) = min( π , I × β ) ridge I* = π / β I = FLOPs / bytes moved from DRAM

    Lab 7A · Interactive roofline

    Pick a machine, slide a kernel

    Worked: SAXPY on RTX 4090

    FLOPs 2N · bytes 12N (read x, read y, write y)

    AI = 0.167 → attainable ≈ 0.167 × 1008 ≈ 168 GFLOP/s, out of 82,600. Even "trivially parallel" kernels are memory-bound.

    Worked: LLM inference

    Prefill processes the whole prompt as a GEMM: compute-bound.

    Decode at batch 1 is a GEMV that reads every weight once per token: 2NK FLOPs over 2NK bytes in FP16, so AI ≈ 1. Memory-bound, which is why batching and disaggregated prefill/decode serving exist.

    Slide catch: L7 quotes decode GEMV at "≈ 2 FLOP/Byte for FP16". Counting it out gives 2NK / (2·NK) = 1. Either way it's far left of every ridge point, so the conclusion holds.

    Nsight, top-down

    • Nsight Systems: whole-app timeline, find the kernel worth fixing
    • Nsight Compute: one kernel, hardware counters
    • Top 5: Speed of Light, Occupancy, Memory Workload, Warp Stall reasons, Roofline
    • Counters are exact; stall reasons are sampled; theoretical occupancy and roofs are calculated ceilings

    Why Tensor Cores exist

    Issuing an instruction costs ~30 pJ; an FP16 FMA costs ~1.5 pJ. Paying 20× overhead per FLOP is silly, so one instruction does a whole D = A×B + C tile. Low-precision A, B; FP32 accumulator.

    Level 8

    Transformers and LLM inference

    RNNs process tokens one at a time and forget. Attention lets every token look at every other in parallel, which suits GPUs, and then the KV cache becomes the memory problem.

    From L8 · Sequence Modeling, Transformers and KV Caching
    RNN / LSTM

    Hidden state carried step to step. Sequential, so it can't parallelise over time, and gradients vanish (LSTM gates help).

    Transformer block

    tokenize → embed + positional encoding → multi-head self-attention → feed-forward, repeated N times.

    Decoder

    Masked (causal) attention: token t only sees ≤ t. Generates autoregressively, one token per step.

    Lab 8A · Self-attention

    softmax(QKᵀ / √d) V, on a toy sentence

    Rows = the token asking (query), columns = tokens it attends to (keys). Each row sums to 1. Hand-picked 4-d vectors with Q = K = 2x, not a trained model. Turn off the √d scaling and the rows get peakier.

    Lab 8B · KV cache

    Memory for compute

    KV bytes = 2 (K and V) × layers × kv_heads × head_dim × seq_len × batch × bytes/elt

    Without a cache each new token recomputes K and V for the whole prefix. With it, each step computes only the new token's K, V and appends. MQA shares one K/V head across all query heads; GQA shares one per group.

    Lab 8C · Depthwise separable conv (MobileNet aside)

    Split spatial filtering from channel mixing

    LLMs, briefly

    • Emergent capabilities appear with scale
    • Zero-shot and few-shot learners; in-context learning from prompt examples
    • Fine-tuning adapts a pre-trained model
    • RAG: retrieve documents, put them in context, then generate

    Positional encoding

    Attention is order-blind, so add a position signal. The original transformer uses sin/cos at different frequencies so relative offsets are easy to learn. Different heads end up capturing different relationships.

    Level 9

    Model compression

    Edge devices need real-time output in little memory, and the cloud adds latency and privacy cost. There's no free lunch, but four tools get close: pruning, quantization, architecture search and distillation.

    From Model Compression · Sys4ML (after Song Han's EfficientML)
    Lab 9A · Pruning

    Zero out the weights that matter least

    Pruning recipe

    • Criterion: usually |w| (magnitude); regularisation pushes weights toward zero first
    • Prune → fine-tune → prune more (iterative) recovers accuracy
    • Layers differ in sensitivity, so prune them by different ratios
    • Unstructured needs sparse hardware; structured runs on anything; Ampere+ Tensor Cores run 2:4 at 2× (Lab 7 table)

    Other tools

    • Low-rank: W ≈ UV with small inner dim
    • NAS: search space + strategy + performance estimate; hardware-aware NAS uses a latency predictor, since MACs ≠ latency
    • Deep Compression: prune + quantize + Huffman
    • Pruning + distillation combine well
    Lab 9B · Linear quantization

    r = S (q − Z)

    S = (rmax − rmin) / (qmax − qmin) Z = round(qmin − rmin/S) q = clamp(round(r/S) + Z)

    Top dots: real weights. Ticks: the 2ᵇ representable levels. Bottom dots: dequantized values. One outlier stretches S and wastes most levels; that's why per-channel scales, mixed precision and non-uniform (k-means codebook) quantization exist. PTQ quantizes a trained model; QAT simulates quantization during training. Extremes: binary (±1) and ternary (−1, 0, +1).

    Lab 9C · Knowledge distillation

    Temperature softens the teacher

    L = α · CE(yhard, ps) + (1 − α) · T² · KL( softmax(zt/T) ‖ softmax(zs/T) )

    A hard label says only "cat". Soft labels also say "a bit dog-like, nothing like a cup". That extra signal is what the small student learns from.

    Bonus level

    Case study: the softmax energy ladder

    The Eval 1 decks in your folder apply everything above to row-wise softmax on an L40S (864 GB/s, 96 MB L2, 350 W cap). Each step changes one thing.

    From PAA Eval 1 · Softmax & LayerNorm (16384 × 4096, DRAM-bound)
    Lab · Energy per call

    Times barely move between clock settings for S2–S8 (~692 µs), because DRAM sets the pace. Lowering the clock removes wasted power.

    Lesson 1

    S0 → S2: 4.4× less energy

    One thread per row reads uncoalesced (32 sectors per load instead of 4) and makes 3 passes. Coalescing and fusing passes hit the DRAM roof (~90% of 864 GB/s).

    Lesson 2

    Memory-bound → energy ≈ bytes

    All optimised FP32 kernels land near 240 mJ. FP16 I/O (S8) halves the bytes and the energy.

    Lesson 3

    Below the cap, fastest ≠ cheapest

    At equal time, instructions per element rank energy. S8 at 900 MHz uses 19% less energy than PyTorch FP16 for 4% more time.

    Everything you'll be asked to compute, in one place.

    Indexing

    idx = blockIdx.x·blockDim.x + threadIdx.x
